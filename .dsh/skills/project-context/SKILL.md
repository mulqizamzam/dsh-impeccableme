# Project context

Establish durable product facts before proposing a solution.

## Procedure

1. Inspect repository instructions, README, routes, primary screens, domain types, tests, and existing product/design documents. Use only host tools actually available.
2. Summarize the product's purpose, primary users, core jobs, business constraints, platform requirements, and relevant technical constraints. Distinguish explicit facts from inferences.
3. Identify the most important unknowns. Ask a focused question only when an unknown materially changes the solution; otherwise state a reversible assumption.
4. Separate durable product truth (audience, purpose, domain, constraints) from surface-specific visual direction.
5. Record the evidence location for material claims. Do not invent user research, analytics, requirements, or stakeholder decisions.
6. When authorized, write a concise project brief to the location the user specifies. Avoid overwriting existing documentation without inspection and approval.

## Output

Provide a short context brief, evidence references, assumptions, unanswered questions, and next recommended step.

## Completion

The brief is grounded in inspected project evidence; unsupported claims and unresolved consequential decisions are visible.
